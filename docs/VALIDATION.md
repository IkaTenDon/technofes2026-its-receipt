# 検証記録

現在の標準手順は `pyproject.toml`、`.python-version`、`uv.lock` による uv 管理です。下記の pip・requirements を使った Python 3.13.7／3.12.10 の記録は、uv 移行前に実施した検証です。移行後の検証結果は本書の末尾に記載しています。現在の依存ライブラリの版は `uv.lock` を参照してください。

検証日は2026年11月7日です。実行先は Windows x64 です。プリンター、USB カメラ、物理ボタンの実機は使用していません。この記録の成功はソフトウェアの自動テスト・環境構築・画像生成についてであり、紙への印字やイベント会場での動作確認を意味しません。

システムに存在した Python 3.13.7 で仮想環境を作り、Pillow 13.0.0、OpenCV 5.0.0、qrcode 8.2、および winsdk を除く上流依存関係を導入しました。`python -m unittest discover -s tests -v` の結果は76件成功、skipなしでした。実行時間は7.312秒でした。[実行ログ](test-python313.txt) を同梱しています。`pip check` と `compileall` も成功しました。

この76件には、SQLite の再起動後の連番維持と8ワーカーによる32件の並行採番、写真なしのカメラ非呼出し、撮影後のカメラ解放、処理中入力の破棄、長押し入力のゲート、受付後の時間間隔、印刷失敗後の同番号・同日時・同画像による再送、撮影失敗時だけの同番号での再撮影、画像期限、再起動後の未解決状態、送信前後の DB 保存失敗が含まれます。プリンターは偽の接続先で検査し、実機への通信は行っていません。

画像テストでは日本語の折り返し、長文による高さの変化、写真による高さの増分、二値画像、整数モジュールの QR と白余白、OpenCV による QR デコード、幅パターンの端線を確認しました。実上流を使うテストでは固定 commit の実カタログを読み、`ConnectedPrinter.raster_job()` で17 pxと257 pxという異なる高さのジョブを生成しました。これにより実在する API とジョブ構築の互換性は検査していますが、上流の機種プロファイルが今回のプリンターに適合することは確認していません。

Windows GUI の4件は、非表示の実 Tk ウィンドウを作り、写真なし受付からメモリ内プレビューの表示と消去、人工写真の見本が採番・撮影しないこと、次の処理をキューに入れないこと、キー解放前の再押下拒否を確認しました。別の1件では Windows のファイルロックで二重起動を拒否し、解放後に再取得できることを確認しました。さらに実アプリの `main()` から設定読込・DB準備・GUI作成・終了までを、撮影・送信なしで起動確認しました。物理ボタンや Windows の実際のフォーカス切替を伴う操作は未検証です。

Python 3.13 では `winsdk==1.0.0b10` の wheel を取得できず、ソースビルドで Visual Studio / nmake 不在による失敗を確認しました。この結果を Bluetooth 実行環境の構築成功とは扱っていません。

続いてシステム設定を変更せず、NuGet の Python 3.12.10 x64 を作業フォルダーへ展開し、別の仮想環境へ `requirements-printer.txt` を導入しました。この環境では winsdk の cp312 wheel を含む全依存関係の導入と `pip check` が成功しました。依存関係の実際の版は [検証環境の freeze](requirements-validated-windows-py312.txt) に保存しています。これは Windows Python 3.12 用の記録であり、他 OS 用の依存一覧ではありません。

Python 3.12.10 での同じテストスイートは76件中72件成功、GUI4件を skip しました。実行時間は6.899秒でした。NuGet の配布に Tcl/Tk が含まれないことを確認しており、GUI を実行できたと主張していません。[実行ログ](test-python312.txt) を同梱しています。実上流ジョブ生成と Windows のファイルロックはこの環境でも成功しました。上流 CLI の `--list-models` 実行も成功しました。Bluetooth 探索や接続を実行した結果ではありません。

標準の Windows 向け Python 3.12 x64 と Tcl/Tk を使った GUI・Bluetooth の組合せ確認、およびイベントで使うすべての実機での受入確認は残っています。カメラの利用権限、画角、照明、撮影時間、Bluetooth の対応機種・経路・ペアリング、物理的な印字幅、紙面 QR の読取率、熱や濃度、長いレシートの連続印刷、紙切れや電源断時の結果は未検証です。手順と期待結果は README に記載しています。

CLI で保存した見本を目視確認し、日本語や縦方向の配置に欠けがないことを確認しました。既定設定で写真なしは384×607 px、人工写真ありは384×879 pxでした。増分272 pxは写真260 pxと要素間隔12 pxです。写真の挿入後に続く領域の画素は一致し、写真なし、人工写真あり、印字幅パターンのすべてから `https://example.com/` を復号できました。これは設定中の仮 URL であり、本番 QR の内容ではありません。人工写真は階調パターンで、実際の人物写真は使用していません。

配布と同じプロジェクトを別の作業フォルダーへコピーし、Windows PowerShell から `scripts/setup.ps1 -PythonExe <Python 3.13.7の実行ファイル>` を実行しました。新規の `.venv` 作成と、開発用 requirements のインストールが成功しました。その直後に `scripts/test.ps1` を実行し、76件中75件成功、印刷用依存未導入の実上流テスト1件を skip しました。実行時間は24.911秒でした。setup/start/test の3つの PowerShell スクリプトは構文検査にも成功しています。`start.ps1` による実際の有人操作は検査しておらず、アプリの入口と Tk 起動は前述の非表示ウィンドウで確認しています。

プリンター制御では、送信前エラーと送信開始後の結果不明を模擬し、後者の再印刷時に重複の可能性を残すことを検査しました。送信と切断が両方失敗する場合、接続準備の解放が失敗する場合、送信前の切断だけが失敗する場合も対象です。接続を安全に解放できなかったインスタンスは次の接続を試さず、アプリ再起動を要求します。これらは偽の接続での例外注入テストです。

現時点の未確定事項はプリンターの型番と接続先、実印字幅、定型文、QR の本番内容です。設定ファイルで変更できる形で保留しています。既知の動作上の限界は、撮影ドライバーの強制タイムアウトを保証しないこと、通信成功でも機種によって機械的な完了を確認できないこと、RAM から画像を破棄した後や再起動後は写真入りレシートを復元できないことです。

uv への移行では、uv 0.11.26 が取得した CPython 3.12.13 Windows x64 を、作業フォルダー内の独立した検証用プロジェクトで使用しました。Python の展開後に Tcl/Tk を含む Tkinter が利用でき、非表示の画面を作成して終了できることを確認しました。このサンドボックスでは `uv python install` の補助的なマイナーバージョンリンク作成が権限で拒否されましたが、展開済みの Python は `uv python find` で検出できています。レジストリ登録や共通の実行ファイル配置は行っていません。

検証用プロジェクトの `scripts/setup.ps1` は、既に取得した Python を uv が検出する状態で実行しました。`uv sync --locked` による新規 `.venv` 作成、winsdk を含む22個の依存パッケージの導入、Tkinter の画面作成確認が成功しました。Python を取得する段階からすべて無条件に成功したという検証ではありません。セットアップ後の `scripts/test.ps1` は76件成功、skipなし、実行時間10.036秒でした。既存のテストケースと受付・撮影・印刷の実装は変更していません。

当日起動の確認では、空の uv キャッシュを指定し、`scripts/start.ps1 -TestMode` を実行しました。`uv sync --locked --offline --check --no-python-downloads` が環境を変更せず整合確認に成功し、続く `uv run --offline --no-sync --no-python-downloads` から実際の受付画面が作成されました。自動確認用のフックで画面を非表示にしてテストモード表示を確認後、終了しています。uv.lock が書き換わらないことも確認しました。通常の有人操作や実機印刷を検証した結果ではありません。

別の検証用設定で pyproject の依存をロックと異なる版へ変更した場合は、同じオフライン整合確認が失敗し、uv.lock を変更しないことを確認しました。uv の直接実行による人工レシート PNG の生成も成功しました。プリンター・カメラ・物理ボタンの実機確認、および既知の二つの状態管理の不具合の修正は、今回の uv 移行には含めていません。
