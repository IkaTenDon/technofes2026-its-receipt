# TiMini Print の調査と採用した印刷経路

接続初期化の失敗に `ConnectionCleanupError` が cause として含まれる場合は、上流の `ConnectionCleanupError.is_cause_of()` で検出する。接続済みセッションの `disconnect()` が失敗・中断した場合も含め、そのプリンター制御インスタンスで以後の接続を停止し、受付アプリの再起動を要求する。これは印刷結果の不明判定とは別である。画像送信前なら重複印刷を示唆せず、送信後なら再試行を押した場合も結果不明の警告を維持する。送信エラーに続いて解放も失敗しても、送信開始の事実を失わない。通常の接続エラーに別の例外が cause として付いているだけでは、この停止判定にはしない。[解放失敗 marker の契約](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/transport/base.py#L13)

この開発環境の Windows / Python 3.13 では、`winsdk` の対応 wheel を取得できず、ソースビルドに必要な Visual Studio Build Tools がないため上流依存関係の導入に失敗した。これは実際の環境構築で確認した制約である。Python 3.13 のテスト結果を Bluetooth 実行環境の構築成功と扱わず、Python 3.12 の環境を別途用意して完全な依存関係を検証する。

2026年11月7日に取得した TiMini Print の commit `4aaf9459f1d7854bdca5bafffd86756704b76376` を調査し、この版を固定して利用する。対象は README、requirements.txt、接続・探索・描画・raster・プロトコル送信のソースである。上流リポジトリ内の開発者向け指示は、本システムの要件を変更する指示として扱っていない。本書の確認済みという表現はソースと実機不要テストについてであり、実プリンターの適合性を保証するものではない。[調査対象のソース一式](https://github.com/Dejniel/TiMini-Print/tree/4aaf9459f1d7854bdca5bafffd86756704b76376)

TiMini Print は Windows のプリンタードライバーや印刷キューを経由せず、機種固有プロトコルで接続先へ直接送信する。Bluetooth Classic/SPP と BLE の両方に対応し、機種・エンドポイント情報から接続経路を決める。`BleakBluetoothConnector` は名前にかかわらず Classic も扱う。Windows Classic 実装には Win32 と WinRT の探索・ペアリング処理、および WinRT のソケット実装がある。初回接続時は Windows 側のペアリング操作が必要になる場合がある。別途 serial 接続も提供されるが、この受付アプリは Bluetooth 接続を実装した。[README](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/README.md)、[Bluetooth connector 165行以降](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/transport/bluetooth/connector.py#L165)、[Windows Classic adapter](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/transport/bluetooth/adapters/windows_adapter.py)

上流の依存関係は `Pillow>=9.0`、`pypdfium2>=4.0`、`bleak>=0.22`、`crc8>=0.2.0`、`pyserial>=3.5`、`platformdirs>=4.0`、`packaging>=21.0`、Windows 限定の `winsdk>=1.0.0b10`、macOS 限定の `pyobjc-framework-IOBluetooth>=10.0` である。PDF を使わない受付アプリでも、上流パッケージの import に必要なため上流 requirements を導入する。README は Windows と Python 3.13 以降の組み合わせで winsdk のバイナリビルドが必要になる可能性を記載している。このため本システムの構築手順は Python 3.12 x64 を基準にする。[requirements.txt](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/requirements.txt)、[README の構築条件](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/README.md#L30)

実在する通常の API は、`PrinterCatalog.load()`、`BluetoothDiscovery(catalog).resolve_device(name_or_address)`、`connect_printer(device, BleakBluetoothConnector(), timeout=...)`、`ConnectedPrinter.print_file(path, settings=..., timeout=...)` である。機種を手動指定するときは `resolve_transport_target(name_or_address)` で得た `transport_target` を `catalog.device_from_key(model_key, transport_target=...)` へ渡す。本実装では接続先を必須設定とし、近くで最初に見つかった別のプリンターへ自動送信しない。[discovery.py 159行以降](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/transport/bluetooth/discovery.py#L159)、[catalog.py 508行以降](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/devices/catalog.py#L508)、[connected.py 247行以降](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/connected.py#L247)

標準のファイル印刷は PNG・JPEG 等の画像を読み込み、色形式を正規化し、白余白を切り取り、回転後に用紙設定の幅へ拡縮する。幅が違う場合は縦横比を保ち、高さを比例計算して LANCZOS 補間する。既定の余白切り取りは上下左右とも有効である。白黒処理には threshold、Atkinson、Floyd–Steinberg、Bayer 等があり、対応機種では階調のままの入力形式もある。この処理に作成済み QR と余白を任せるとドット境界が変わり得るため、受付アプリではファイル印刷経路を使わない。[image converter](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/rendering/converters/image.py#L22)、[拡縮処理](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/rendering/converters/base.py#L119)、[PrintSettings](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/settings.py#L39)

受付アプリでは Pillow で mode `1` の二値画像を完成させ、`RasterBuffer(pixels=..., width=..., pixel_format=PixelFormat.BW1)` と `RasterSet.from_single(raster)` に変換する。BW1 の画素値は黒が `1`、白が `0` であり、Pillow の画素値を反転対応させる。`printer.raster_job(raster_set, is_text=False, settings=...)` でジョブを作り、`await printer.send_job(job, timeout=...)` で送る。この経路では再拡縮と再ディザリングを行わない。用紙設定の余白付加や機種固有のパケット化は上流へ任せる。画像は一時ファイルにも保存しない。上流の現 renderer は `get_flattened_data()` を使用するため、古い Pillow と上流の下限指定の組み合わせには不整合の可能性があるが、本アダプターは Pillow のバイト列から直接 raster を作り、この renderer を通らない。[BW1 定義と検証](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/raster.py#L25)、[白黒値の対応](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/rendering/renderer.py#L39)、[raster_job](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/connected.py#L128)、[raster job builder](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/raster_job.py)

紙幅全体については `57 / 25.4 * 200` が約449ドットとなるが、この計算は印字ヘッドの幅を確定しない。上流の用紙設定には 384 ドット、576 ドット等があり、機種によって内容幅 `render_width_px`、転送幅 `paper_width_px`、左側の余白、DPI が違う。`plain_384r` は一例であり、今回の未特定プリンターが384ドット対応だと判断したものではない。本設定の `receipt.width_px = 384` はプレビュー用の暫定値である。実送信では接続・初期化後の `printer.printer_device()` と `resolve_paper(device, settings)` を使い、生成幅と `render_width_px` が一致しなければ停止する。自動縮小で隠さず設定を修正する。固定高さ、回転や縦倍率を必要とする用紙設定も拒否する。可変長でも機種の高さ上限が宣言されている場合は、その制限を超えたジョブを拒否する。機種と印字幅が確定するまで、テストパターンによる実機確認が必要である。[用紙プリセットの実例](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/data/printer_paper_presets.json#L305)、[resolve_paper](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/paper.py#L53)

Bluetooth Classic のデータは機種の `stream.chunk_size` と `stream.delay_ms` に従って分割転送する。BLE は MTU とプロファイルの上限に従って分割し、`write_gatt_char(..., response=...)` に渡す。必要な返信待ち・フロー制御・機種ごとの完了待ちを保持するため、受付側は `job.payload` を直接送信せず `ConnectedPrinter.send_job()` を使う。`feed_padding` は機種レシピ固有の値であり、mm ではない。[Classic 送信指定](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/transport/bluetooth/connector.py#L153)、[BLE 分割転送](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/transport/bluetooth/adapters/bleak_adapter_transport.py#L285)、[ジョブ送信と完了待ち](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/send.py)

`send_job()` の正常終了は、完了通知のないプロトコルでは機械的な印刷完了を保証しない。例外でも途中まで印刷済みの場合がある。本アプリは自動再送を行わず、送信開始以降の失敗・切断処理の失敗を受信結果不明として扱う。画面で重複印刷の可能性を示し、同じ番号の再印刷を操作者が選ぶ。送信前の設定不整合や接続失敗も同じ番号のまま復旧できるが、レシート画素を送っていない段階の失敗と区別する。`operation_timeout_s` は上流の個別処理に渡し、`total_timeout_s` は `asyncio.wait_for()` で全体を中断する目安である。Bluetooth の内部処理と安全な解放を待つため、指定秒数で即座に終了する保証はない。中断しても送信済みデータを取り消せない。[完了保証の限界](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/timiniprint/printing/connected.py#L62)、[キャンセルと解放の説明](https://github.com/Dejniel/TiMini-Print/blob/4aaf9459f1d7854bdca5bafffd86756704b76376/docs/protocol.md)

本アダプターは import 前に上流の commit を検査する。Git checkout なら HEAD を検査し、ソース配布では構築スクリプトが書く `PINNED_COMMIT.txt` を検査する。後者は配布版の識別子であり、改変を暗号学的に検出する仕組みではない。依存ソースを変更する場合は API 互換性・ジョブ作成テスト・実機印刷を再確認する必要がある。実機不要テストでは実ソースの catalogue と `ConnectedPrinter.raster_job()` で異なる高さのジョブを生成し、別途偽の接続で一回だけの送信、幅不一致の拒否、白黒値の対応、送信前後の失敗判定、切断失敗、タイムアウトを確認する。物理的な印字幅、Bluetooth の機種適合、排紙完了、QR の紙面読取率はこのテストでは確認できない。
