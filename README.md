# technofes2026-its-receipt

Windows の受付画面で F1 を押すと写真あり、F2 を押すと写真なしのレシートを作る Python アプリです。写真なしではカメラを開きません。Tkinter、Pillow、OpenCV、SQLite を使い、Bluetooth 印刷は同梱した TiMini Print の実在する raster API を呼び出します。HTTP サーバーやブラウザーは起動しません。初期設定は実印刷を行わないテストモードです。

この配布物はアプリの実装であり、未特定プリンターへの適合を実機で確認した製品ではありません。機種名、Bluetooth 接続先、実際の印字幅、定型文、QR の内容は未確定です。`config.toml` に変更箇所を示しています。384 px はプレビュー用の暫定幅であり、紙幅57 mm・200 dpiから導いた確定仕様ではありません。調査した上流の版とソース根拠は [TiMini Print 調査記録](docs/TIMINI_RESEARCH.md)、実行した検証と未検証範囲は [検証記録](docs/VALIDATION.md) にあります。

## Quick start

このシステムは、Windows PC で受付画面を開いておき、来場者が写真あり・なしを選ぶたびに一件ずつレシートを印刷します。初回だけ実行環境と本番用設定を用意します。その準備が済んだ PC では、当日は機器の接続、試し刷り、受付画面の起動から始めます。イベント中は同じ画面を開き続け、最後のレシートの確認が終わってから終了します。

初回は、Python と依存ライブラリを管理する `uv` 0.11.26以降を用意します。既に `uv --version` でその範囲のバージョンが表示される場合は、そのまま使えます。未導入で WinGet を利用できる Windows では、PowerShell で次のコマンドを実行します。ほかの導入方法は [uv の公式説明](https://docs.astral.sh/uv/getting-started/installation/)を参照してください。

```powershell
winget install --id=astral-sh.uv -e
```

導入後は PowerShell を開き直し、`uv --version` が表示されることを確認します。このプロジェクトは Windows x64 と Python 3.12 を対象にしています。Python 3.13 では今回の環境で印刷用の winsdk の導入に失敗したためです。Python 3.12 の選択は `.python-version`、依存ライブラリの版は `uv.lock` で管理し、必要な Python がなければ `uv` が取得します。画面表示に必要な Tcl/Tk を利用できることは、後述のセットアップ時に確認します。

PowerShell を開き、プロジェクトを置いたフォルダーへ移動します。PowerShell は、文字のコマンドでプログラムを起動するための画面です。下の `C:\配置した場所\technofes2026-its-receipt` は記入例なので、エクスプローラーのアドレスバーからコピーした実際のフォルダーのパスへ置き換えてください。以降のコマンドも、このフォルダーを開いた同じ PowerShell で実行します。

```powershell
Set-Location -LiteralPath 'C:\配置した場所\technofes2026-its-receipt'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup.ps1
```

このコマンドは `uv sync --locked` を実行し、プロジェクト専用の Python 環境である `.venv` と、カメラ・画像生成・Bluetooth 印刷に必要なライブラリ一式を用意します。続いて Tkinter を使った画面を作成できることを確認します。初回の導入にはインターネット接続が必要です。最後に `Setup complete` と表示されたら準備完了です。エラーが出た場合はその状態で受付を始めず、表示された内容を確認してください。当日の `start.ps1` は環境の整合性を確認してから起動し、ダウンロードや環境更新は行いません。このセットアップを毎日の起動時に繰り返す必要もありません。

次に、USB カメラと物理ボタンを接続し、プリンターの電源と用紙、PC の Bluetooth を確認します。物理ボタンは、写真ありが F1、写真なしが F2 のキーボード入力を送る設定にします。ほかのスマートフォンやアプリがプリンターを使っている場合は接続を閉じます。機種により Windows 側でペアリング操作が必要です。プリンターの名前やアドレスを調べるには、受付アプリを閉じた状態で次のコマンドを実行します。

```powershell
$env:TIMINIPRINT_NO_UPDATE_CHECK = '1'
uv run --offline --no-sync --no-python-downloads python .\vendor\TiMini-Print\timiniprint_command_line.py --scan
```

本番用設定は `config.local.toml` に保存します。次のコマンドは、まだ本番用設定がなければ `config.toml` をコピーし、メモ帳で開きます。既存の本番用設定はコピーで上書きしません。

```powershell
if (-not (Test-Path -LiteralPath .\config.local.toml)) {
    Copy-Item -LiteralPath .\config.toml -Destination .\config.local.toml
}
notepad .\config.local.toml
```

メモ帳では、`[receipt]` の `title`、`body`、`footer` を実際の文面に、`qr_data` を本番の QR コードの内容に変更します。`[printer]` の `bluetooth_target` には、探索で確認した対象プリンターの名前またはアドレスを記入します。同名の機器がある場合はアドレスで区別します。`model_key` は通常は空のままにし、自動判別できない場合だけ、実機に適合する TiMini の機種キーを指定します。紙幅だけから機種を推測して指定しないでください。

紙へ印刷するには、`[app]` の `test_mode = true` を `test_mode = false` に変更して保存します。`true` はプリンターへの送信だけを止める設定で、採番と、写真ありの場合のカメラ撮影は実行します。来場番号を保存する `database_path` は、イベント中と番号を継続する次回の運用で同じものを使います。試し刷りを含む受付操作にも番号は発行されるため、番号と実際の来場人数は一致しません。設定変更はアプリの再起動後に反映されます。

開場前に、まず印字幅確認用パターンを印刷します。`receipt.width_px` の初期値384は暫定値であり、今回のプリンターの実印字幅と確定したものではありません。次のコマンドは、来場番号を発行せずに確認用画像を保存し、本番用設定に従って印刷します。受付アプリを閉じた状態で実行してください。

```powershell
uv run --offline --no-sync --no-python-downloads python -m receipt_app --config config.local.toml width-pattern --output width-test.png --print
```

紙の左右の端線が欠けていないこと、文字が読めること、QR コードを読み取ると設定した内容になることを確認します。幅不一致のエラーが出た場合は、表示された機種の幅と用紙設定を確認して設定を修正します。自動縮小はしません。白紙、欠け、圧縮、白黒反転、QR の読み取り失敗がある場合は、解決してから受付に進みます。実際に紙が出て読めることを、本番開始の条件にしてください。

確認ができたら、次のコマンドで受付画面を起動します。設定済みの PC で当日起動するときも、このコマンドを使います。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -Config config.local.toml
```

画面上部の「本番モード：Bluetoothへ送信します」を確認します。「テストモード：実印刷しません」と表示されている場合は紙が出ません。設定の `test_mode` と、起動コマンドに `-TestMode` を付けていないかを確認してください。また、画面が開いて「待機中」になっただけでは Bluetooth 接続の成功は確認できません。プリンターへの接続は印刷するときに行います。

開場前に、実際の物理ボタンで写真あり・なしをそれぞれ試します。写真ありは先にカメラに向いて撮影の準備をしてから F1、写真なしは F2 を押します。撮影前のカウントダウンはありません。写真なしではカメラを起動しません。紙に印刷された写真・文面・日時・QR と、物理ボタンの動作まで確認してから、来場者の受付を始めます。

受付中は画面を前面に置きます。ほかのウィンドウを操作した後は、受付画面のタイトルバーをクリックして入力先を戻してください。入力先が受付画面になっていないと、物理ボタンを押しても受付されません。来場者が写真あり・なしを選んで一度ボタンを押したら、撮影・画像作成・印刷処理が終わるまで待ちます。その間の次の入力は予約されず、破棄されます。

「印刷処理完了」と表示されたら、画面だけでなく実際に出た紙を確認します。機種によって、アプリからは機械的な印刷完了まで確認できないためです。紙に問題がなければ来場者へ渡し、次の受付に進みます。「待機中」という表示への自動復帰を待つ必要はなく、既定では処理終了から1秒後に次の操作を受け付けます。毎回「受付を閉じる」を押す必要はありません。

紙が出ない、途中で止まる、エラーが表示される場合は、次の来場者のボタンを押す前にその受付を処理します。紙とプリンターの状態を確認し、必要なら「同じ番号で再試行・再印刷」を使います。画像が保持されていれば、同じ番号・日時・画像を再送します。既に印刷済みの可能性があるため、確認画面の重複印刷の説明を読んでから実行します。撮影または画像作成で失敗し、まだレシート画像がない場合は、同じ番号で撮影から再試行します。

再印刷用画像は、既定では処理終了から120秒だけ保持します。次の受付開始、画像の明示的な破棄、アプリ終了でも失われます。保持期限後や再起動後には、同じ写真入りレシートを復元できません。したがって、紙の確認を済ませてから次の受付に進みます。復旧できずにその受付を打ち切る場合は、紙の状態を確認したうえで「画像を破棄して受付を閉じる」を押します。これは印刷成功を記録する操作ではなく、その受付を終了して次の受付を可能にする操作です。

現在は、エラー中にウィンドウを閉じるとその受付が破棄済みになる不具合と、再試行で以前の「印刷結果不明」の警告が消える不具合が残っています。一度でも印刷結果が不明になった番号は、後の警告が消えても未印刷と判断できません。再起動が必要な場合は、閉じる前に番号と紙の状態を確認・記録してください。接続の解放失敗を示すエラーでは、アプリが再接続を停止するため、この確認を済ませてから再起動します。

用紙補給などで中断するときは、進行中の一件の処理と紙の確認を終えてから、次のボタン操作を止めます。専用の一時停止ボタンはありません。機器の復旧ができない場合は、印刷受付を停止します。この一件ずつの受付と紙の確認を、イベント終了まで繰り返します。

終了時は、最後のレシートの受け渡しと、未解決の受付の扱いを確認してから受付画面を閉じます。処理中は通常の閉じる操作を受け付けません。アプリを終了した後にプリンターなどの電源を切ります。次回も番号を継続する場合は、`config.local.toml` と、そこに指定した番号保存用データベースを残してください。データベースを削除して番号を初期化する操作は、通常の終了手順には含めません。

## 開発・設定・検証の詳細

実行環境は `uv` で管理します。アプリと印刷用の依存関係は `pyproject.toml` にまとめ、具体的な導入版は `uv.lock` に固定しています。セットアップの `--locked` は、ロックファイルを変更せず、設定と一致する版を導入する指定です。Python は `.python-version` と `pyproject.toml` の指定に従って3.12系を使用します。依存関係の更新はイベント前に検証する作業として行い、受付当日の起動時には行いません。[uv のプロジェクト管理](https://docs.astral.sh/uv/guides/projects/)、[ロックと同期の説明](https://docs.astral.sh/uv/concepts/projects/sync/)

PowerShell でプロジェクトフォルダーへ移動し、開発時も次のコマンドで準備してテストモードを起動できます。ExecutionPolicy の指定は、この PowerShell プロセスだけに適用されます。既存の Python を明示して環境を作る場合は、セットアップに `-PythonExe 'C:\実際の場所\python.exe'` を追加してください。指定する Python は3.12 x64で、Tcl/Tkを利用できる必要があります。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -TestMode
```

PowerShell の補助スクリプトを使わずに準備する場合は、同じフォルダーで `uv sync --locked` を実行します。セットアップスクリプトはこの同期に加えて Tkinter の動作確認を行います。準備済みの環境では、次のように Python の入口を直接起動することもできます。

```powershell
uv sync --locked
uv run --offline --no-sync --no-python-downloads python -m receipt_app --test run
```

`--offline --no-sync --no-python-downloads` は、起動時にネットワークから取得せず、依存関係を同期せず、Python の自動取得も行わない指定です。直接の `uv run` では依存環境の整合性確認は行わないため、導入後に `pyproject.toml` や `uv.lock` を変更した場合は先にセットアップをやり直してください。当日の起動スクリプトでは `uv sync --locked --offline --check --no-python-downloads` による確認を行い、不一致なら受付画面を起動せず停止します。

TiMini Print のソースは `vendor/TiMini-Print` に固定版を同梱しているため Git のインストールや最新版への追従は不要です。ソースを勝手に更新せず、API を変更する際は再検証してください。日本語フォントは同梱せず、既定では Windows の `C:/Windows/Fonts/meiryo.ttc` を読み込みます。別の日本語フォントを使う場合は、利用権を確認したフォントのパスと必要なら `font_index` を設定してください。

受付画面には状態、現在の来場番号、写真の選択、エラー内容、レシートのプレビューを表示します。画面にフォーカスを置いた状態で物理ボタンを押してください。物理ボタンは通常の USB キーボードとして F1/F2 を送信する設定にします。管理者権限やグローバルなキーボードフックは使用しません。キーは押下から物理的な解放を確認するまで一度しか受理せず、処理終了後にも既定で1000 msの受付間隔を設けます。処理中の入力はキューに積まず破棄します。エラーを未解決のまま次の番号を発行しません。

「写真あり」では受付ごとにカメラを開き、準備用フレームを読み、撮影後は必ず解放を試みます。「写真なし」は撮影関数を呼び出しません。OpenCV の `device_index`、希望解像度、準備フレーム数、`dshow` / `msmf` / `any` は設定できます。ドライバーが内部で停止した場合、OpenCV の open/read を指定秒数で強制中断する保証はありません。処理は GUI と別スレッドですが、その間は次の受付を禁止します。

実機に触れずに見た目を確認するには、画面の見本ボタンを使えます。人工写真の見本もカメラを開きません。見本の来場番号は1で、SQLite の採番には影響しません。次のコマンドは同じ見本を PNG に保存します。保存するのは人工画像だけであり、来場者の写真を保存するコマンドは用意していません。

```powershell
uv run --offline --no-sync --no-python-downloads python -m receipt_app preview --output preview-no-photo.png
uv run --offline --no-sync --no-python-downloads python -m receipt_app preview --photo-sample --output preview-with-synthetic-photo.png
uv run --offline --no-sync --no-python-downloads python -m receipt_app width-pattern --output width-test.png
```

レシートには受付操作時の番号と PC の現在日時・UTC オフセットを印字します。番号、日時、定型文、QR、余白は写真の有無で共通です。写真領域だけを追加または省略するため、写真なしは短くなります。文章はフォントの実測幅で折り返し、要素の高さを積み重ねて画像を作ります。写真は中心を切り抜いて設定サイズに合わせ、グレースケール、コントラスト・ガンマ補正、Floyd–Steinberg の二値化を適用します。文字と QR は写真のディザリングを通りません。QR は誤り訂正 M、4モジュールの白余白、整数ドットのモジュールで生成し、設定した最小ドット数で収まらない場合は縮小せずエラーにします。これは画像上の読取性への対策であり、紙面の読み取りを保証しません。

本番用の設定は `config.toml` を `config.local.toml` へコピーして編集すると区別できます。文面は `[receipt]` の `title`、`body`、`footer`、`qr_data` を変更します。複数行の文面には TOML の三重引用符を使えます。余白、文字サイズ、写真の高さも同じセクションです。相対パスは設定ファイルのあるフォルダーを基準に解決し、変更後はアプリを再起動します。番号を継続する場合は `[app].database_path` を同じ DB に向けてください。テスト受付も本番と同じ採番を行うため、イベント前の試運転には `data/test.sqlite3` のような別 DB を使うと区別できます。

プリンターを接続する際は電源と Bluetooth を有効にし、スマートフォンの印刷アプリなど他の接続を閉じます。機種により Windows の Bluetooth 設定で初回ペアリング操作が必要です。ドライバーによる通常の Windows 印刷キューは使いません。TiMini の探索と機種一覧は次の公式 CLI で確認できます。自動更新確認は環境変数で無効にしています。

```powershell
$env:TIMINIPRINT_NO_UPDATE_CHECK = '1'
uv run --offline --no-sync --no-python-downloads python .\vendor\TiMini-Print\timiniprint_command_line.py --scan
uv run --offline --no-sync --no-python-downloads python .\vendor\TiMini-Print\timiniprint_command_line.py --list-models
```

`[printer].bluetooth_target` へ探索結果の名前またはアドレスを明示します。同名機がある会場ではアドレスを使って区別してください。`model_key` は自動判別できない場合だけ、実機に適合する既知のキーを指定します。モデルを推測して指定すると別プロトコルを送ることになるため、57 mmという紙幅だけから選ばないでください。`paper_preset` は空なら機種の既定で、必要ならその機種の可変長ロール紙設定へ変更します。固定長のラベル、回転・縦倍率を要する設定はこのアプリでは拒否します。

印字幅は生成画像と、接続・機種準備後の TiMini `render_width_px` を照合します。違う場合は送信前に停止し、実際の設定幅をエラーで示します。上流に登録された幅と物理的に印字できる幅が一致することまでは保証しないため、実機で印字幅テストが必要です。本番用設定で `test_mode = false` にし、次のコマンドを使うと来場番号を発行せずテストパターンを送信できます。`--print` がない場合は PNG の作成だけです。`--test` または `test_mode = true` の場合は `--print` があっても送信しません。

```powershell
uv run --offline --no-sync --no-python-downloads python -m receipt_app --config config.local.toml width-pattern --output width-test.png --print
```

印字した紙で左右の端線、0から最終列までの目盛り、8ドット刻みが欠けずに見えることを確認します。設定が384なら右端は383です。端線が欠ける、全体が圧縮される、白黒が反転する場合は本番受付に進める状態ではありません。機種、用紙プリセット、余白を再確認してください。QR を実際の読み取り機器で読み、`qr_data` と一致することを確認します。濃度は文字・QR・写真を同時に見て `blackening` と写真の補正を調整します。`feed_padding` は機種固有単位で、mmではありません。

本番の起動は設定ファイルを明示して行います。コマンドに `-TestMode` を追加すると設定より優先して実印刷を無効にできます。起動中に設定を読み替える機能はありません。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -Config config.local.toml
```

来場番号は SQLite の `INTEGER PRIMARY KEY AUTOINCREMENT` により受付操作に対して発行します。写真あり・なしで同じ連番を共有し、再起動後も継続します。実際の入場人数の厳密な計数ではありません。撮影や印刷に失敗した番号も使用済みです。DB には番号、日時、写真選択、状態、試行回数、エラー文だけを保存し、画像・画像パスは保存しません。印刷直前の状態保存に失敗した場合は送信せず、送信後の状態保存失敗は印刷結果不明として扱います。同じ DB を使うアプリの二重起動は OS のファイルロックで拒否します。

送信に失敗しても自動で新番号を発行せず、自動再送もしません。「同じ番号で再試行・再印刷」は保持中の同じレシート画像を使うので、番号・日時・写真は変わりません。撮影または画像作成の段階で失敗し、まだレシート画像がない場合だけ、同じ番号・日時で撮影から再試行します。送信開始後の切断やタイムアウトでは部分印刷済みの場合があり、同番号でも再印刷すると重複します。正常終了時も機種によって機械的な排紙完了を確認できないため、画面は用紙確認を求めます。接続の安全な解放に失敗した場合は同じプロセスで再接続せず、画面の指示に従ってアプリを再起動する必要があります。

再印刷とプライバシーの両立のため、撮影画像は合成後に解放し、完成レシート画像だけを RAM に保持します。処理終了から既定120秒、次の新規受付、「画像を破棄して受付を閉じる」、アプリ終了のうち最初の時点で画像への参照を破棄します。GUI の実写真入りプレビューも同時に消します。処理中には送信に必要なため期限破棄しません。RAM や Windows のページファイル・クラッシュダンプからの完全消去はこのアプリでは保証しません。

画像保持期限後、またはアプリの再起動後は、写真入りレシートを復元できません。この設計は写真の永続保存をしない方を優先しています。未解決の失敗が残る場合は番号と結果不明の説明を表示し、再印刷を無効にして新規受付も止めます。紙とプリンターを人が確認し、「受付を閉じる」でその受付を終了できます。その操作後の新しい受付には新番号が発行されます。画像を失ったまま同番号の写真を自動的に撮り直すことや、エラーを新規受付へ自動変換することはありません。

実機を使わない自動テストは、セットアップで依存関係一式を導入した後、次のコマンドで実行します。連番の永続化・並行採番、撮影分岐とカメラ解放、画像寸法と QR デコード、失敗時の同番号再印刷、送信前後の SQLite 失敗、保持期限、未解決状態の復旧、Windows GUI、長押し抑止、二重起動、上流 API による実ジョブ生成を検証します。GUI テストは非表示の Tk ウィンドウを作成し、ハードウェアには接続しません。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\test.ps1
```

実機の受入確認では、まず別のテスト DB とテストモードで F2 を押し、カメラの使用表示が点灯せず短いレシートが表示されることを確認します。続いて F1 でカメラが起動し、撮影後に解放され、写真分だけ長くなることを確認します。実際の物理ボタンで長押しと連打を行い、処理中の押下が後から印刷されず、長押し一回が一件になることを確かめます。ウィンドウからフォーカスを外した状態の F1/F2 では受付されないことも確認します。

印字幅パターンと QR の紙面確認が済んだら、本番モードとテスト DB で F1/F2 の双方を印刷します。共通項目が同じで写真領域だけが異なること、Bluetooth 再接続を含む連続運用で欠けや途中停止が起きないことを確認します。途中でプリンターの電源を切るか接続を失わせ、エラー後に新規入力が停止すること、同番号再試行に重複警告があることを確認します。電源断の瞬間によっては実際には印刷済みなので、紙を必ず確認します。

保持期限を過ぎたときに実写真プレビューが消えて再印刷できなくなること、アプリを再起動して番号が増分を保つこと、失敗中の強制終了後に前回未解決の番号が表示されることも実機確認の対象です。強制終了ではアプリの通常の解放処理は走らず、番号や画像の復元より重複の回避を優先して停止します。イベントで使用する PC、カメラ、物理ボタン、プリンター、ロール紙、読み取り機器の組み合わせで確認して初めて実機検証済みといえます。

トラブル時に日本語フォントを開けない場合は `font_path` と `font_index`、QR が収まらない場合はデータ長・設定幅・余白を確認します。カメラを開けない場合は Windows のカメラのプライバシー設定でデスクトップアプリの利用を許可し、他のカメラ利用アプリを閉じ、デバイス番号と backend を変更して確認します。撮影が長時間止まる場合はドライバー内停止の可能性があり、強制終了後の前回未解決状態に注意します。

Bluetooth 探索や接続に失敗する場合は、電源、距離、Windows の Bluetooth、初回ペアリング、他のアプリによる接続占有、接続先アドレス、モデル対応を確認します。白紙や途中までの紙が出る場合も再試行は重複し得ます。印字幅不一致は自動縮小せず止まる仕様です。SQLite に書き込めない場合は DB フォルダーの書き込み権限と空き容量を確認してください。番号を維持する必要がある DB を削除して解決しないでください。ロックファイルは残っていても、OS ロックはプロセス終了時に解放されるためファイル削除は通常不要です。

構成上は `camera.py` が撮影、`storage.py` がメタデータと採番、`rendering.py` が Pillow のレイアウト、`printer.py` が上流との接続、`controller.py` が受付の状態と画像寿命、`gui.py` が Tkinter とキー入力を担当します。`config.py` は TOML の読み込みと検証です。レイアウト変更は `render_receipt()` の要素配置と設定値で行えます。安全のため画像全体の高さを30000 px、画素数を3200万までに制限しますが、これは固定長レシートという意味ではなく、長文設定による過剰なメモリ使用を防ぐ上限です。プリンター固有の宣言された高さ上限がある場合はそれも検査します。
